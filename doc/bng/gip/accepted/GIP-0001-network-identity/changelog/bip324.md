# BIP324 (v2 transport) test-vector notes (GIP-0001)

This document records why `bip324_tests` fails in BNG after the GIP-0001 “network identity” changes, and provides a concrete step-by-step plan to make the test pass *for BNG*.

## What BIP324 is (short)

BIP324 specifies the “v2” encrypted P2P transport for Bitcoin-like nodes.
At a high level it:

- Negotiates a shared secret between peers (using ElligatorSwift / x-only secp256k1 keys).
- Derives traffic keys using HKDF-SHA256.
- Encrypts/authenticates packets (ChaCha20-Poly1305) and adds metadata like a session id.

The important property for this fork: the key schedule is intentionally *bound to the network* via a salt component derived from the P2P message start (“magic”) bytes.

## What `bip324_tests` is doing

`src/test/bip324_tests.cpp` contains `packet_test_vectors`, which verifies that given fixed inputs (static keys, plaintext, etc) the implementation produces exact byte-for-byte expected outputs:

- `cipher.GetSessionID()`
- `cipher.GetSendGarbageTerminator()`
- `cipher.GetReceiveGarbageTerminator()`
- the full ciphertext (or a suffix comparison depending on the vector)

It also runs a “corruption” loop that flips bits in the ciphertext and checks decryption failures behave as expected.

## Why upstream vectors fail in a fork

BNG changes network identity parameters per GIP-0001, including the 4-byte P2P message start bytes (see `src/kernel/chainparams.cpp`, summarized in `changelog/chainparams.cpp.md`).

The BIP324 implementation in this tree derives its HKDF salt from:

- a constant label (e.g. `"bitcoin_v2_shared_secret"`)
- **plus the network’s message start bytes** (`Params().MessageStart()`)

Because HKDF is sensitive to every input bit, changing the message start bytes changes:

- the derived session id
- the garbage terminators
- the packet keys
- the resulting ciphertext

So if the hard-coded vectors in `src/test/bip324_tests.cpp` were produced using Bitcoin mainnet magic (historically `f9beb4d9`), they will not match BNG mainnet magic (e.g. `BNG\x01`), even when the BNG code is correct.

This is the same class of issue as BIP32 vectors failing when Base58 version bytes change, except here the network identity is part of the cryptographic salt rather than a string encoding.

## What we observed when running the test

When running only the failing unit test (`bip324_tests/packet_test_vectors`), the first failures appear as mismatches in:

- session id equality checks
- send/receive garbage terminator checks
- ciphertext comparisons

Once the base vector mismatches, the later corruption/decryption loop produces a large “failure explosion” because it expects the initial derived state to match.

## Recommended fix direction for BNG

**Regenerate the expected test vectors for BNG’s message start bytes.**

Do *not* “force Bitcoin magic” in BNG’s BIP324 implementation just to satisfy upstream vectors:

- It would contradict GIP-0001’s goal (network separation).
- It would make the test validate a key schedule the BNG node does not actually use.

A test-only override of the message-start used in the HKDF salt can be useful as a temporary debugging tool, but should not be the final state for BNG.

## Step-by-step plan to make `bip324_tests` pass on BNG

1. **Reproduce the failure in isolation**
   - In the build dir, run only the failing test:
     - `ctest -R '^bip324_tests$' --output-on-failure`
     - or `./bin/test_bitcoin --run_test=bip324_tests/packet_test_vectors`

2. **Confirm the network binding is the cause (one-time sanity check)**
   - Verify BNG’s mainnet message start bytes in `src/kernel/chainparams.cpp`.
   - Verify `src/bip324.cpp` uses `Params().MessageStart()` as part of the HKDF salt.

3. **Decide the intended semantics for the test in BNG (choose one)**
   - **Option A (recommended):** keep the test as a strict byte-for-byte vector test, but update the vectors to BNG-derived expected outputs.
   - Option B (debug-only / not recommended long-term): temporarily add a test-only knob to derive using Bitcoin mainnet magic so you can compare against upstream vectors.

4. **Create a reliable “vector dump” of computed outputs (implementation support step)**
   - In `src/test/bip324_tests.cpp`, add (or temporarily enable) logging right after the cipher is constructed for each vector that prints:
     - the message start bytes actually used
     - computed session id
     - computed garbage terminators
     - computed ciphertext (or the compared suffix)
   - Prefer Boost.Test logging (`BOOST_TEST_MESSAGE`) so output follows Boost.Test log settings.

5. **Run once to dump computed expected values for BNG**
   - Run with message logging enabled and redirect output:
     - `./bin/test_bitcoin --run_test=bip324_tests/packet_test_vectors --log_level=message --report_level=no > bip324_vectors_bng.txt 2>&1 || true`
   - Ensure the dump contains full hex for each computed value.

6. **Update the hard-coded vectors in `src/test/bip324_tests.cpp`**
   - Replace the expected `session_id`, `garbage terminators`, and `ciphertext` bytes in the vector table with the BNG-computed values.
   - Keep the *inputs* (keys/plaintext) unchanged, unless they were also tied to Bitcoin-specific encodings.

7. **Remove or gate any temporary logging**
   - Delete the dump logging, or gate it behind a compile-time flag if you want to keep it available without noise.
   - Keep the test output clean under normal CI runs.

8. **Re-run only `bip324_tests`**
   - `ctest -R '^bip324_tests$' --output-on-failure`

9. **Guard against future regressions**
   - Add a small assertion in the test that the message start bytes match the BNG expectation for the selected chain (so future chainparams edits don’t silently invalidate vectors).
   - Keep this assertion minimal and local to the test.

10. **Update the GIP checklist**
   - Once green, check off “Test #18: bip324_tests” in `doc/bng/gip/accepted/GIP-0001-network-identity/test/happy-tests.md`.

## Notes on scope

- This plan aims to fix *only* `bip324_tests` and keep the rest of the suite untouched.
- The fix is intentionally “fork-correct”: it preserves the network identity binding in BIP324 rather than bypassing it.
